# Resource engineering rules

These user-approved defaults apply to this repository and its bundled FiveM resources. They are copied from the FiveM workspace AGENTS.md so they remain available in standalone checkouts. Existing resource-specific contracts and documented behavior must be preserved when applying them. Runtime compliance must be established from source review and validation; this file alone is not proof of compliance.

## Workspace engineering principles

These are user-approved defaults for all scripts in this workspace, with the strongest compatibility requirements applying to `np_*` resources. Apply them to new work and use them when reviewing existing implementations.

- **Performance:** Aim for the best practical runtime and resource efficiency. Pay special attention to hot loops, frequent network events, database work, entity enumeration, and client/server tick handlers. Prefer measured improvements and avoid needless polling, duplicate work, and unbounded queries. Preserve correctness, security, and useful extension points; note material performance tradeoffs.
- **Resource compatibility:** `np_*` resources should discover and integrate with other running `np_*` resources automatically when a supported integration is available. Also make integrations possible with non-`np_*` resources where the platform and their APIs allow it. Detect optional resources safely, use documented exports/events/contracts, tolerate resources being absent or restarting, and provide graceful fallbacks. Keep optional integrations optional; do not introduce hidden hard dependencies or expensive discovery loops. Use adapters/configuration for differing APIs instead of spreading resource-specific assumptions through core logic.
- **Customization and documentation:** Expose broad, stable customization surfaces so server developers can adapt behavior without editing core logic: documented exports, events/callbacks, configuration, and extension hooks as appropriate. Document names, side (client/server), arguments and types, return values, permissions, lifecycle, examples, and failure behavior. Keep editable configuration and supported extension points available even when a resource uses FiveM escrow; do not make essential customization depend on changing escrowed internals. Treat APIs as contracts and document compatibility changes.
- **Server authority and validation:** Treat every client-provided value and event as untrusted. Make the server authoritative for identity, permissions, ownership, money, inventory, rewards, cooldowns, distance, and consequential state changes. Validate type, range, current server state, and rate limits at the point of use; derive sensitive values on the server instead of accepting client calculations. Design handlers to resist replay, duplication, race conditions, and resource restarts. Keep client checks useful for experience, never as the security boundary.
- **Anti-cheat:** Look for practical opportunities to strengthen server-side detection and prevention, including when touching related gameplay or event code. Prefer robust signals, bounded logging, and reviewable enforcement; account for false positives and avoid trusting client-reported evidence as proof. Keep anti-cheat changes compatible with legitimate resource integrations and measure operational impact.

When these principles compete, preserve server-side security and correctness first, then meet performance and customization goals within those constraints. Record any user-approved exception in the relevant repository's durable project instructions or design documentation.
